# 识别数据在哪里，后续怎样调用

2026-11-03 更新。本文针对独立工程`abc20261102`，不连接旧系统的数据通道或数据库。数据分为最新状态、实时消息、历史日志三类；网页画面只是其中一个消费者。

## 已有存储和调用入口

| 需要 | 入口 | 保存范围 |
|---|---|---|
| 网页查看最新结果 | `http://192.0.2.11:28880/lab` | 最新画面、人物和7B摘要 |
| 程序读取最新精简状态 | 同一地址的`GET /api/state` | 最新视觉观测、7B和更新年龄 |
| 程序读取最新完整结果 | `GET /api/raw-state` | 完整最新`observation`和`llm`，不是历史查询 |
| 连续接收视觉结果 | MQTT `labs/abc20261102/v1/runs/<run_id>/observations` | JSON结果消息；传输压缩方案见下文 |
| 连续接收7B结果 | 同一路径末尾`/llm` | 非逐帧的7B解释 |
| 查询／导出历史 | 控制云`/srv/abc20261102/data/events.jsonl` | 控制端实际收到的事件，按行追加 |
| 控制云断线时仍留生产端结果 | 启用`result_journal`后，生产端工程的`data/results/<run_id>/<role>-<producer_instance_id>.jsonl` | 每条实际生成的完整视觉观测，先写本机再尝试网络发布 |

HTTP沿用控制台登录认证。`192.0.2.11`是Pi的局域网IP，热点换网后可能改变。MQTT控制broker监听控制云回环28883；Pi/GPU通过自己的独立SSH通道接入，没有开放公网MQTT端口。当前B/C图像经控制云28883转发；图像与结果使用独立MQTT连接，专用GPU直连28583作为历史备用配置，当前停用。

最新HTTP状态存于Node-RED内存。**停止、开始新实验、服务重启会清掉最新状态；磁盘历史日志仍保留。** `/api/state`和`/api/raw-state`不能查询以前某轮结果。当前没有数据库、历史HTTP列表或完整原视频下载接口；标准库导出工具可直接处理已有JSONL。

## 最简单的HTTP调用

先在网页启动实验，再在能访问Pi局域网的设备上运行以下Python。只用标准库，账号密码从输入读取，不写进代码或项目。

```python
import base64
import getpass
import json
import urllib.request

user = input("控制台账号：")
password = getpass.getpass("控制台密码：")
auth = base64.b64encode((user + ":" + password).encode()).decode()
req = urllib.request.Request(
    "http://192.0.2.11:28880/api/raw-state",
    headers={"Authorization": "Basic " + auth},
)
with urllib.request.urlopen(req, timeout=10) as response:
    state = json.load(response)
observation = state.get("observation")
if observation is None:
    print("当前没有运行中的识别结果")
else:
    print(observation["run_id"], observation["source_frame_id"])
    for person in observation.get("tracks", []):
        print(person["track_id"], person["posture"], person["clothing"])
```

这适合低频获取最新值。持续高频业务优先在Pi／控制云已有通道一侧订阅MQTT，不应通过不断轮询HTTP获取每一帧。使用者应检查结果年龄与实验ID，过期或未知结果不能当成当前有效测量。

## 结果字段与关联方法

视觉顶层含`project`、`run_id`、`arm`、`source`、`source_frame_id`、`source_pts_s`、`encoded_size`、`jpeg_sha256`、`producer`、`status`、`infer_ms`、`timing`和`tracks`。每个人的结果包含：

- `track_id`、`bbox`：本轮临时轨迹和识别输入图坐标，不能把ID当成跨实验身份。
- `posture`、`action`、`window`：姿态、动作候选和时序证据是否充分。
- `clothing`、`clothing_age_s`：衣物候选／置信度及其更新年龄。
- `clo`、`met`、`estimate_status`、`visible_clo_reference`：当前数值仍为`null`，可见衣物标准参考候选不等于人体整体热阻实测。

新结果另含`producer_instance_id`和`observation_seq`：每次Worker启动生成新的UUID，每轮序号从1递增。去重生产结果用`run_id + producer_instance_id + observation_seq`；人物轨迹还应包含`track_id`。图像／视觉的同帧关联仍使用`run_id + source_frame_id`，同时检查生产实例重启情况，不能把重启后重置的ID当成原来的人物。旧历史可能没有新字段，不能凭空补出实例身份。

7B返回依据的`source_frame_id`、`model`、`status`、`draft.summary`、`draft.uncertainty`和`generation_ms`；不要把较早帧的7B输出当成当前逐帧结果。`generated`仅代表通过现有格式／已知错误检查，仍需人工验证内容；`rejected`和`failed`不能按成功结果消费。

当前结构化输出没有保存完整17点骨架，虽模型内部使用了骨架。`cross_machine_age_ms`仍为空，跨机时钟未校准；不能直接用不同机器时间戳相减声称端到端延迟。服饰未检出不表示没有衣服，动作未知也不能换成一个猜测的MET值。

## 历史导出：完整JSONL和逐人CSV

在控制云的新工程目录运行，`YOUR_RUN_ID`替换为网页最新状态或历史中的真实`run_id`：

```bash
cd /srv/abc20261102
python3 tools/export_results.py --run-id YOUR_RUN_ID --output data/exports/run.jsonl --people-csv data/exports/people.csv
```

默认读取脚本所属工程的`data/events.jsonl`。完整JSONL保留原记录、未知字段、时间戳与其他消息，不只导出人物。CSV只展开`observations`，一条人物轨迹一行；零人物观测保留一行`row_type=empty_observation`和`track_count=0`。`clo/met`空值导出为空单元格，**不写成0**。CSV保留`producer_instance_id`、`observation_seq`、`producer_recorded_wall_ms`三个关联列，旧记录没有则留空。嵌套衣物、框、窗口和标准参考值保存在JSON列；JSONL仍是完整事实的首选格式。

按通道筛选或读取已经下载的历史副本：

```bash
python3 tools/export_results.py --input results/events-performance-routes.jsonl --run-id YOUR_RUN_ID --channel observations --channel llm --output results/selected.jsonl --people-csv results/selected-people.csv
```

`--run-id`和`--channel`均可重复；不填表示不筛选。不填`--output`时完整JSONL写到标准输出，记录计数写到标准错误。输入、JSONL输出和CSV输出不能使用同一路径。工具流式读取文件，不把所有历史装入内存。损坏行会报告行号并退出；若当时正在追加日志，应在一轮结束、最后一行完整后导出。报错退出可能留下部分输出，不能把部分文件当完整导出。

磁盘日志每行一般为：

```json
{"channel":"observations","console_boot_id":"…","received_mono_ms":123.4,"received_wall_ms":1790000000000,"payload":{"run_id":"…","source_frame_id":42,"tracks":[]}}
```

日志记录控制端**实际收到**的数据，不承诺每次推理绝不漏记。`result_qos`默认0，可在配置中改变；即使改为QoS1，接受发布也不能当成控制云已落盘，重复消息还需按实例与序号去重。断线、发送拥塞和最新值覆盖可能造成缺帧。分析时需要结合`result_stats`、`transport_stats`、`cloud_stats`和停止后迟到记录。图像预览在内存中只缓存最近24帧，JSONL记的是预览元数据，不是JPEG本体。**没有完整连续相机视频或每一张识别图像的存档**，已有日志不能替代后续准确性所需的视频和人工标签。

## 生产端留档与网络故障后的补查

配置`result_journal=true`时，统一观测发布函数先将完整、未压缩结果追加到生产端JSONL，并逐行flush到操作系统，再尝试MQTT发布。默认false便于保留未启用留档的基线。A组由Pi写`edge-<实例UUID>.jsonl`；B/C组由GPU写`cloud-<实例UUID>.jsonl`。文件惰性创建：B/C的Pi只传图而不生成完整视觉观测时，不会空建一个观测日志。

每行结构与完整JSONL导出兼容：

```json
{"channel":"observations","producer_recorded_wall_ms":1790000000000,"payload":{"run_id":"…","producer_instance_id":"…","observation_seq":1,"source_frame_id":42,"tracks":[]}}
```

会话结束关闭文件，并发送`result_stats`事件：`generated`、`accepted_for_publish`、`publish_rejected`、`raw_journal_bytes`、相对工程的`journal_path`、`journal_enabled`、`qos`及实例ID。`accepted_for_publish`仅表示发布函数接受，不表示PUBACK、更不表示控制云历史文件已写入。网络不可用而发布返回0时，本机已经flush的结果仍在。磁盘写入、flush或关闭失败会报告`failed`并停止该会话，不伪装为已经保存成功。

GPU端可直接用同一个工具导出：

```bash
cd /root/abc20261102
.venv/bin/python tools/export_results.py --input data/results/YOUR_RUN_ID/cloud-YOUR_INSTANCE_ID.jsonl --output data/exports/local-run.jsonl --people-csv data/exports/local-people.csv
```

Pi上在`/home/pi/abc20261102`运行，并选择`edge-…jsonl`。也可以将生产端文件复制到分析设备后通过`--input`读取。生产端记录没有控制云收到时的时间和boot ID，相应CSV列留空；`producer_recorded_wall_ms`不能跨机直接当延迟。

**本机留档不等于自动回补控制云。** 当前没有后台补传、自动合并或断电恢复事务。逐行flush没有执行每行`fsync`，不提供突然断电后最后若干条必然保存的保证。文件只包括实际生成的观测，不包括因为采样、未收到图像或推理前丢弃而从未生成的结果；7B结果和完整原图也不在这个观测日志里。若源端也未收到新图，留档不会凭空补出观测。

## 传输改进：无损结果压缩

`lab/result_codec.py`提供标准JSON与gzip level1的兼容编解码，不改字段、数值、阈值或模型。`encode_json(value, compress=False)`默认plain；启用时只对足够大的JSON压缩，压后不更小则仍发plain。`decode_json(payload)`根据标准gzip头自动识别，解压上限默认8MiB。损坏或超限包会报错，不悄悄改成空结果。

主链路启用时，只压缩`observations`消息体；Pi/GPU发布端、7B适配器、Node-RED接收端须成套更新。解压后的历史JSONL与HTTP字段保持原结构，JPEG预览不再套gzip。MQTT订阅者若直接`json.loads(msg.payload)`将不能读取压缩消息，应改为：

```python
from lab.result_codec import decode_json
observation = decode_json(msg.payload)
```

本地真实回放样本245条观测，plain均值约8809B，gzip level1约1949B，减少约78%。本地Python3.12.3下，JSON编码加gzip的p50/p95约0.449/0.603ms，解压加JSON解析约0.422/0.595ms；字段、数值和Python类型逐项比对全部一致。这不是Pi或GPU的压缩耗时，也不表示整链路帧率已提高。样本来自`results/events-performance-routes.jsonl`的`daff8451-4e3f-4884-80be-24b721998040`轮。当前压缩是否启用、实跑吞吐和延迟结论，以`config.json`和本轮对照结果为准；不能只看到压缩模块存在就宣称链路已启用压缩。

## 本轮传输更新：Pi本地预览

浏览器入口仍是Pi的28880端口，PC仅充当查看器。`/live-video`、`/api/preview-frame`、`/api/preview`、`/api/preview-meta`由Pi回环28990的aiohttp服务响应，经过原Caddy登录认证；`/api/state`、`/api/raw-state`、控制和7B仍来自控制云。云端不再发送预览JPEG，只发送完整视觉结果和7B结果。多个浏览器的预览图片分发发生在局域网，不需要每个浏览器从云端下载一遍图片。

Pi缓存最多120个送检原JPEG，预览缓存64帧；这是短期内存缓存，不是录像存档。停止/换轮会清空；指定已经失效的帧返回410。后台慢浏览器只保留一个最新待发包，超时后断开并由页面重连。浏览器预览ACK不再发给云端，避免把本地预览错误计成云端到屏幕延迟；7B ACK保留。

预览头新增`pi_capture_to_preview_ms`，用同一台Pi的单调时钟测量采集读取完成至同帧预览生成，包含送检、云端推理、结果返回和Pi编码，但**不含曝光前端、局域网下发、浏览器绘制/屏幕扫描**。页面“处理ms”显示该指标；“更新几秒前”只是页面接收后的年龄。

`POST /api/start`可增加`sample_fps`，范围1–30（当前采集目标30）；省略时使用部署默认。例如`{"arm":"C","source":"camera","seconds":60,"sample_fps":12}`。该目标会记入本轮命令和源端事件；不是每秒保证交付的帧数。做A/B/C放置比较时须统一此参数、源视频、编码与模型版本。

结果QoS1、去重和生产端逐条JSONL已启用，但断线期间没有自动历史回填。需要完整审计时同时导出生产端日志，按`run_id+producer_instance_id+observation_seq`核对，不要把控制端实时流当作无损数据库。

真实导出验收示例：控制云`data/exports/recovery-run.jsonl`含511条事件，`recovery-people.csv`含405条观测行；本地副本在`results/exports/`。序号字段保留，clo/met空单元格未变成0。
